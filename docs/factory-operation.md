## 1. 결론

`tossminiapps`는 Paperclip 중심 프로젝트가 아니라 **앱 공장(factory) 중심 프로젝트**로 운영한다.

- DM: 앱 후보 우선순위, 수익화/정책 리스크, 운영 방식 결정
- tossminiapps 전용 채팅: 실제 구현/빌드/QA/승인 패키지 작업
- 체크리스트: 기본 운영 단위
- Kanban: 3호 앱 이후 병렬 생산이 필요할 때 사용
- Paperclip: 승인/리뷰/역할별 critique trail이 필요할 때 제한적으로 사용

목표는 앱 하나를 깊게 완성하는 것이 아니라, 공식 Apps in Toss 규격 안에서 여러 앱을 빠르게 만들고 학습을 축적하는 것이다.

## 2. Paperclip / Kanban / 파이프라인 보드 역할

### 체크리스트

가장 기본 운영 도구다.

사용할 때:
- 새 미니앱을 만들 때
- 앱별 빌드/광고/공유/결과 카드/승인 항목을 점검할 때
- 반복 작업을 빠르게 끝낼 때

장점:
- 빠르다.
- 오버헤드가 낮다.
- 10개 앱 생산에 적합하다.

단점:
- 담당자/이슈/댓글 trail은 약하다.
- 병렬 작업이 많아지면 상태가 흩어질 수 있다.

### Kanban

3호 앱 이후부터 적극 사용한다.

사용할 때:
- 앱 여러 개를 동시에 만들 때
- `콘텐츠 작성`, `구현`, `QA`, `listing asset`, `승인 패키지`를 나눠야 할 때
- profile별 작업을 자동 배정하고 싶을 때

장점:
- 실행 상태를 빠르게 볼 수 있다.
- `tossminiapps` assignee로 작업을 격리할 수 있다.
- 반복 생산 큐에 적합하다.

단점:
- 앱별 정책/승인 문맥을 길게 남기기엔 Paperclip보다 약하다.
- 너무 세분화하면 오히려 생산 속도가 떨어진다.

기본 명령:

```bash
hermes kanban create "tossminiapps 3호 앱 MVP 생성" \
  --assignee tossminiapps \
  --tenant tossminiapps \
  --workspace dir:/Users/jinsik/Desktop/Workspace/01_project_tossminiapps \
  --body "tossminiapps 전용 작업. 다른 프로젝트 접근 금지. 공식 Apps in Toss/TDS 기준으로 3호 앱 MVP를 생성하고 build/모바일 QA 기준을 기록한다."
```

### 파이프라인 보드

tossminiapps에는 매우 잘 맞는다.

추천 상태:

1. 후보
2. 정책 리스크 검토
3. MVP brief 작성
4. 구현 중
5. 빌드 통과
6. 모바일 QA
7. listing asset 준비
8. 승인 패키지 준비
9. 제출 대기
10. 제출/운영 중

장점:
- 앱 10개 생산 상태를 한눈에 보기 좋다.
- 각 앱의 병목이 어디인지 빠르게 보인다.
- 콘텐츠/디자인/개발/승인 흐름을 분리할 수 있다.

단점:
- 실제 파일/테스트 검증은 별도 필요하다.
- 보드만 이동하고 산출물 검증을 안 하면 의미가 없다.

### Paperclip

초기에는 보조로만 쓴다.

사용할 때:
- 앱 승인/리뷰 패키지를 공식 기록으로 남길 때
- 여러 역할의 critique가 필요한 앱일 때
- 특정 앱의 정책 리스크나 광고 배치 판단을 남겨야 할 때
- 10개 앱 전체 현황을 회사/팀 단위로 관리하고 싶을 때

장점:
- 역할별 의견과 증거를 남기기 좋다.
- 승인 패키지/검수 기록에 유리하다.

단점:
- 앱을 빠르게 찍어내는 초기에는 무겁다.
- 에이전트가 실제 산출물 없이 지침 확인만 할 수 있다.
- 빌드/스크린샷/asset 검증은 결국 Hermes가 해야 한다.

운영 결론:
- 1~2호 앱: 체크리스트 중심
- 3~5호 앱: 파이프라인 보드 + Kanban 도입
- 6호 이후: 필요하면 Paperclip으로 역할/리뷰/승인 trail 강화

## 3. 새 앱 생성 표준 흐름

### 1단계: 앱 후보 검수

확인 항목:
- 5~10초 안에 이해되는가?
- 결과 카드가 공유될 만한가?
- 광고 보상 명분이 자연스러운가?
- 정책 리스크가 낮은가?
- TDS/공식 WebView 패턴으로 구현 가능한가?

피해야 할 주제:
- 금융상품 추천, 대출/보험/카드 중개
- 투자 조언, 가상자산, 사행성
- 의료/진단/상담
- 현금성 보상을 오해시키는 표현
- Toss Points와 혼동될 보상 표현

### 2단계: MVP brief 작성

각 앱마다 최소 포함:

```text
appName:
displayName:
한 줄 후킹:
사용자 액션:
질문/선택 수:
결과 유형:
공유 포인트:
광고 보상 지점:
재방문 루프:
정책 리스크:
필요 asset:
완료 기준:
```

### 3단계: 템플릿 선택

사용자가 직접 Deus/TDS 화면을 고르게 하지 않는다. 에이전트가 앱 유형에 맞게 선택한다.

앱 유형:
- 테스트형: 질문 5~8개 → 결과 유형
- 짧은 선택형: 2택/3택 반복 → 즉시 결과
- 방어/전투형: 함정/몬스터/방패 메타포
- 체크리스트형: 오늘 점검 → 결과/보상
- 데일리형: 오늘의 콘텐츠 → 7일 기록

기본 원칙:
- 비게임 WebView는 TDS 사용을 기본으로 한다.
- 커스텀 CSS는 브랜드 감도 보완 수준으로 제한한다.
- 질문 중간 광고는 피하고, 결과/상세/보상 지점에 광고를 둔다.

### 4단계: 구현

구현 순서:
1. 앱 폴더/설정 확인
2. 콘텐츠 데이터 작성
3. 홈 화면
4. 질문/액션 화면
5. 결과 카드
6. 공유 버튼/stub
7. 광고 CTA/stub 또는 SDK 연결
8. 재방문/히스토리/스탬프 루프
9. listing copy/asset 준비

### 5단계: 검증

필수:
- `npm run build` 성공
- 모바일 375~390px 화면 확인
- 홈/질문/결과/광고 CTA 확인
- 결과 유형 매핑 확인
- 공유 fallback 확인
- 앱 이름, `granite.config.ts`, 색상, 아이콘 확인
- dev 링크/테스트 버튼이 production에 노출되지 않는지 확인

### 6단계: 학습 축적

앱 하나 완료 후 반드시 업데이트:
- `docs/lessons-learned.md`
- `docs/app-factory-checklist.md`
- `docs/common-template-decisions.md`
- `docs/debug-log.md`

기록할 것:
- 반복 오류
- 빌드/SDK/TDS 주의사항
- 잘 먹힌 후킹/카피
- 재사용 컴포넌트
- 다음 앱에서 바꿔야 할 파일 목록
- deploymentId / `.ait` / listing asset 상태

## 4. 멀티에이전트 역할 분리

### Hermes

역할:
- PM/오케스트레이터/최종 검증자
- 앱 후보 우선순위 정리
- 작업 분해
- 파일/빌드/스크린샷 검증
- 사용자 보고

하면 안 되는 것:
- 에이전트 완료 보고를 그대로 믿기
- 정책 리스크 검토 없이 앱 구현 들어가기
- 다른 프로젝트 파일 접근

### Codex

역할:
- 빠른 구현
- 반복 수정
- 빌드 오류 해결
- 단순 리팩터링

적합한 작업:
- 콘텐츠 JSON 교체
- 결과 카드 UI 수정
- 광고 stub 연결
- 빌드 에러 수정

### Claude Code Sonnet

역할:
- TDS/UX 구조 리뷰
- Apps in Toss SDK 연동 검토
- 복잡한 디버깅
- 결과 카드/후킹 카피 개선
- 코드 품질 리뷰

사용 시점:
- 화면이 토스앱처럼 안 보일 때
- 광고/공유/SDK 구조가 헷갈릴 때
- 앱의 UX 감도가 떨어질 때
- 반복 가능한 템플릿으로 승격하기 전

### 이미지 생성

역할:
- listing asset 원본 이미지
- 앱 내 hero/result illustration
- 캐릭터/몬스터/오브젝트 이미지

주의:
- 한글 텍스트는 이미지 생성에 맡기지 않는다.
- no-text 이미지 생성 후 Pillow/HTML로 한국어를 합성한다.
- 얼굴/손/글자 왜곡을 Vision QA한다.

## 5. 앱별 완료 기준

완료라고 말하려면 아래 중 해당 항목이 검증되어야 한다.

- 코드: build 성공
- 화면: 375~390px QA
- 결과: 결과 유형/점수 매핑 정상
- 광고: 지원/미지원 fallback 정상
- 공유: 공유 문구/fallback 정상
- asset: listing 이미지/카피 준비 상태 명시
- 승인: 제출 패키지 문서 존재
- 학습: lessons/checklist/debug 문서 업데이트

## 7. 당분간의 운영 결론

- tossminiapps는 Paperclip보다 체크리스트/파이프라인이 먼저다.
- Kanban은 앱 수가 늘어나는 순간부터 생산 큐로 쓴다.
- Paperclip은 승인/리뷰/정책 판단 trail이 필요할 때만 쓴다.
- 1개 앱이 끝날 때마다 팩토리 문서를 업데이트해 다음 앱 시간을 줄인다.
