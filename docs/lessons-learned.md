     3|## 2026-05-04 — 7호 후보 `몽글 매치 퍼즐` 게임 템플릿
     4|
     5|- Toss 게임 문서는 첫 화면 디자인 템플릿보다 게임 프로필/리더보드/점수 제출/프로모션/시작 속도/출시 체크리스트가 핵심이다. 게임은 일반 테스트형 미니앱과 별도 `game-template` 계열로 다룬다.
     6|- 게임 프로필은 공식적으로 시작 전 최초 1회 등록 흐름이 있고, 프로필 생성 전 게임 진행이 막혀야 한다. 로컬 MVP는 mock profile fallback을 두되 실제 토스 QA에서 프로필 모달을 확인한다.
     7|- 리더보드 점수 제출은 게임 종료 후 1회만 호출해야 하며, 리더보드 열기 시 미니앱이 백그라운드로 전환되므로 playId/보드/점수 상태를 저장하는 구조가 필요하다.
     8|- 게임 카피는 `포인트 지급/현금 보상`을 약속하지 않는다. 실제 `grantPromotionRewardForGame`은 사업자/비즈월렛/프로모션 코드/게임 카테고리/앱 버전 조건이 맞을 때만 사용한다.
     9|- 3매치 MVP는 기존 최신 WebView seed 복사 후 `src/lib/gameLogic.ts`와 `src/lib/tossGameCenter.ts` adapter를 분리하면 빠르게 구현·빌드 가능하다.
    10|- 단순 3매치만으로는 재방문 이유가 약하므로 `한 판 종료 → 랜덤 몽글 획득 → 희귀도 보너스 → 리더보드 점수 상승 → 도감 누적` 루프를 홈/결과 화면의 핵심으로 둔다.
    11|- 수집형 100종 캐릭터는 소품만 바뀐 반복 실루엣이면 “비슷함/징그러움” 피드백이 생길 수 있다. 100종 확장 전 기존 성공 캐릭터(유령, 탐정/도둑)의 단순 얼굴·역할 소품·작은 사건성을 기준으로 12종 샘플 컨택트시트를 먼저 승인받는다.
    12|- 3매치 보드는 클릭-클릭 선택만 두면 모바일에서 답답하다. 포인터 스와이프/드래그로 인접 칸을 바로 교체하고, 클릭-클릭은 보조 접근성 조작으로 남기는 편이 자연스럽다.

## 2026-05-11 — 몽글 광고 체리피킹형 한 화면 앱

- 한 화면에서 광고 칸을 항상 노출하고, 페이지 전환 없이 반복 탭 가능한 패턴이 유효했다.
- 긴 루틴 카드보다 큰 터치 오브젝트 + 항상 보이는 광고 칸 + 짧은 상태 문구 조합이 390px에서 더 안정적이다.
- 광고 카피는 `광고 보고`처럼 확정형보다 `광고 칸/광고 자리` 같은 슬롯 표현이 안전하다.
- 1스크린 유지가 목표면 보조 진행 카드는 과감히 줄이고, 하단 광고 닻을 고정하듯 두는 편이 낫다.

## 2026-05-29: 09~12 몽글 게임 UX 보강 교훈

- 게임은 첫 화면에서 장르보다 조작과 목표가 먼저 읽혀야 한다. `도망 몽글`은 좌/우 두 버튼만 남기고 `별은 먹고 바위는 피한다`를 첫 카드와 플레이 보드에 반복하니 목적이 훨씬 분명해졌다.
- 플레이 중 재미는 점수 숫자보다 즉시 피드백에서 나온다. 별/무지개 획득, 바위/구름 충돌, 아슬 회피 같은 짧은 임팩트 문구와 애니메이션을 공통 패턴으로 둔다.
- `1초 탐정 몽글`처럼 규칙이 추상적인 게임은 보드 위에 `무엇을 고르는 게임인지`를 별도 case brief로 박아야 한다. 제목만으로는 사용자가 룰을 추론하지 않는다.
- 모든 게임에 `StageRail`을 둬 현재 단계와 다음 단계 문구를 같이 보여준다. 실제 스테이지가 단순 점수/라운드 기반이어도 사용자는 다음 목표가 보여야 계속 누른다.
- 광고 훅이 TDS 토스트를 쓰면 `TDSMobileAITProvider` 없이 로컬 브라우저가 빈 화면이 될 수 있다. 광고/토스트 훅을 이식할 때는 `main.tsx` Provider까지 같이 복사한다.

## 2026-05-29: 몽글 게임 레벨/난이도 교훈

- `StageRail`은 안내 장치일 뿐이고, 실제 규칙이 바뀌지 않으면 사용자는 반복 플레이 이유를 느끼지 못한다. 레벨이 있다면 속도, 배치, 정답 규칙, 보상 주기 중 최소 하나는 판마다 바뀌어야 한다.
- 관찰 게임은 단일 표식 찾기로 만들면 즉시 소모된다. `1초 탐정 몽글`은 색상+표식+소품+표정처럼 2~3개 이상의 속성을 조합해야 “1초 관찰”의 긴장감이 생긴다.
- 정답을 CSS class나 고정 role로 드러내면 게임성이 무너질 수 있다. UI에 보이는 정보는 단서 속성만 두고, 정답 여부는 룰 매칭 결과로만 판단한다.
- 자동 QA에는 “단계 문구 존재”뿐 아니라 “레벨별 데이터 배열 존재”, “이전 단순 판별 로직 제거” 같은 회귀 검사를 넣어야 후속 복제 때 재미 요소가 빠지지 않는다.

## 2026-05-31: 07 몽글 매치 퍼즐 출시 보강 교훈

- 3매치류는 `3개 제거`만 반복되면 손맛이 약하다. 4개, 5개, 가로세로 동시 매치마다 점수 배율과 임팩트 문구를 다르게 두면 같은 조작도 보상 기대가 생긴다.
- 매치 후 드롭/리필에서 새 3개 줄이 생기면 즉시 다시 판정해 연쇄로 터뜨려야 한다. 한 번만 제거하고 멈추면 사용자가 눈으로 본 “맞았다”와 게임 판정이 어긋난다.
- 보드에 현재 매치도 없고 가능한 인접 스왑도 없으면 사용자는 막혔다고 느낀다. 매치 후보가 0개인 정체 상태는 자동 셔플해서 최소 1개 이상의 다음 수를 보장한다.
- 특수 매치는 점수만 올리기보다 다음 행동을 바꾸는 이미지형 아이템을 줘야 체감 보상이 크다. 키보드 이모지는 빠른 스케치에는 편하지만 출시 직전 캐주얼 게임에서는 허접한 HTML 조합처럼 보이므로 앱 고유 에셋으로 교체한다.
- 홈/플레이/모달은 기능을 넣는 순간 첫 화면 조작성이 쉽게 밀린다. 시작 CTA와 메뉴는 도감 미리보기보다 위에 두고, 플레이 중 아이템 독은 한 줄 전체 폭을 써야 390px에서 터치 가능한 크기가 나온다.
- 단순 그라데이션 배경과 평평한 버튼은 게임 느낌이 약하다. CSS 레이어 배경, 80% 갈색 외곽선, 유광 하이라이트, 하단 그림자를 공통 토큰으로 두면 레퍼런스형 캐주얼 게임 톤을 빠르게 맞출 수 있다.
- 메뉴/모달은 타이틀과 닫기 버튼을 절대배치할 때 모바일 높이에서 쉽게 잘린다. 390px QA에서 title/close의 top 값, panel scrollWidth/clientWidth, document overflow를 수치로 확인한다.
- 홈 화면처럼 세로 스크롤이 생기는 컨테이너에서 모달을 카드 내부 `absolute`로 띄우면 사용자가 아래쪽 버튼을 누른 시점의 스크롤 위치 때문에 모달 상단이 화면 밖으로 밀릴 수 있다. 전체 화면 모달은 viewport 기준 `fixed` 레이어로 띄운다.
- 출시 직전 캐주얼 게임 자산은 SVG로 직접 그린 임시 아이콘보다 imagegen 기반 PNG 스프라이트를 쓰는 편이 훨씬 앱답게 보인다. 단, 투명 배경 crop 결과와 실제 보드 naturalWidth/naturalHeight를 QA에서 확인해야 한다.
- 단계 상승은 내부 state만 올리면 사용자가 알아차리지 못한다. 결과 화면에 `완료 단계 -> 다음 단계`를 별도 카드로 보여주고, 홈에는 `다음 판 단계`라고 명시해야 다음 판 목표가 보인다.
- 단계 수가 실제 데이터 배열 길이와 연결되어 있으면 임시 4단계 구성도 곧 제품 한계가 된다. 캐주얼 퍼즐은 최소 10단계 이상의 난이도 사다리를 먼저 만들고, 결과/스테이지 목록에서 `현재/전체`와 레벨별 별/코인 기록을 같이 보여줘야 성장이 보인다.
- 유광 버튼을 만들 때 좌상단 흰 타원 highlight를 모든 버튼 pseudo-element로 넣으면 금세 반복 장식처럼 보인다. 앱다운 느낌은 큰 원형 하이라이트보다 그라데이션, 하단 그림자, 눌림 상태만으로 잡는 편이 안정적이다.
- 보상형 CTA는 성공 여부가 화면에 남아야 한다. `보너스 몽글 찾기`처럼 수집 보상을 주는 버튼은 localStorage만 바꾸지 말고 결과 화면에 즉시 보너스 카드가 떠야 기능이 있다고 느껴진다.
- 게임 BGM은 파일이 없어도 Web Audio 신시사이저 루프로 MVP를 만들 수 있다. 다만 자동재생 제한 때문에 첫 사용자 터치 뒤에 시작하고, 효과음과 설정을 분리한다.
- 광고 SDK는 실제 ID가 없을 때 placeholder를 그리지 않고, 보상형은 `userEarnedReward` 콜백에서만 보상을 지급해야 출시 번들/검수 리스크가 줄어든다.
- 매치 점수 피드백은 화면 중앙 토스트보다 터진 블록 묶음 근처의 작은 플로팅 숫자가 낫다. 보드 중앙을 가리면 다음 낙하/연쇄를 보는 재미가 줄어드니, 매치 key들의 중심점을 계산해 로컬 위치에 띄운다.
- 캐주얼 게임 메뉴를 앱답게 만들 때 버튼 전체를 PNG로 만들면 한글 길이와 반응형이 쉽게 깨진다. 버튼은 CSS와 live 텍스트로 유지하고, 타이틀 플라크/닫기/기능 아이콘/장식 패널처럼 질감이 필요한 부분만 imagegen PNG로 분리한다.
- imagegen이 `transparent background` 요청에도 체크보드나 크로마 배경을 실제 픽셀로 줄 수 있다. 생성 직후 alpha 채널을 확인하고, 필요하면 크로마키 제거/crop/contact sheet/브라우저 naturalWidth 검증까지 한 번에 묶어야 한다.
- 캐주얼 퍼즐의 첫 화면은 캐릭터 뽑기 이벤트보다 “현재 단계, 보드 미리보기, 보상, 게임 시작”을 먼저 보여주는 로비가 더 자연스럽다. 시작 전 안내도 모달로 막기보다 홈 카드 안에 넣어야 토스 다크패턴 리스크가 낮다.
- 보상형 광고 fallback을 `연습 +3`처럼 별도 보상으로 노출하면 실제 광고 완료 보상과 제품 규칙이 흐려진다. 광고가 준비되지 않았을 때는 CTA를 숨기거나 준비 메시지만 보여주고, 보상은 광고 완료 이벤트에서만 지급한다.
- 진동은 브라우저 `navigator.vibrate`만 쓰면 토스앱 실기기 체감이 불확실하다. Apps in Toss WebView에서는 `generateHapticFeedback`을 우선 호출하고 브라우저 진동은 fallback으로만 둔다.

## 2026-05-31: 18 주식 파이터 교육 게임 교훈

- 금융 소재 앱은 실제 종목, 실시간 가격, 투자 판단 문구를 빼고 “교육용 상식 퀴즈 + 가상 차트”로 경계를 고정해야 검수 리스크가 줄어든다.
