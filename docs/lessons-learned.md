# Lessons Learned

## 2026-05-04 — 7호 후보 `몽글 매치 퍼즐` 게임 템플릿

- Toss 게임 문서는 첫 화면 디자인 템플릿보다 게임 프로필/리더보드/점수 제출/프로모션/시작 속도/출시 체크리스트가 핵심이다. 게임은 일반 테스트형 미니앱과 별도 `game-template` 계열로 다룬다.
- 게임 프로필은 공식적으로 시작 전 최초 1회 등록 흐름이 있고, 프로필 생성 전 게임 진행이 막혀야 한다. 로컬 MVP는 mock profile fallback을 두되 실제 토스 QA에서 프로필 모달을 확인한다.
- 리더보드 점수 제출은 게임 종료 후 1회만 호출해야 하며, 리더보드 열기 시 미니앱이 백그라운드로 전환되므로 playId/보드/점수 상태를 저장하는 구조가 필요하다.
- 게임 카피는 `포인트 지급/현금 보상`을 약속하지 않는다. 실제 `grantPromotionRewardForGame`은 사업자/비즈월렛/프로모션 코드/게임 카테고리/앱 버전 조건이 맞을 때만 사용한다.
- 3매치 MVP는 기존 최신 WebView seed 복사 후 `src/lib/gameLogic.ts`와 `src/lib/tossGameCenter.ts` adapter를 분리하면 빠르게 구현·빌드 가능하다.
- 단순 3매치만으로는 재방문 이유가 약하므로 `한 판 종료 → 랜덤 몽글 획득 → 희귀도 보너스 → 리더보드 점수 상승 → 도감 누적` 루프를 홈/결과 화면의 핵심으로 둔다.
- 수집형 100종 캐릭터는 소품만 바뀐 반복 실루엣이면 “비슷함/징그러움” 피드백이 생길 수 있다. 100종 확장 전 기존 성공 캐릭터(유령, 탐정/도둑)의 단순 얼굴·역할 소품·작은 사건성을 기준으로 12종 샘플 컨택트시트를 먼저 승인받는다.
- 3매치 보드는 클릭-클릭 선택만 두면 모바일에서 답답하다. 포인터 스와이프/드래그로 인접 칸을 바로 교체하고, 클릭-클릭은 보조 접근성 조작으로 남기는 편이 자연스럽다.

## 2026-05-04 — 6호 `영수증 몬스터 잡기`

- 5호 seed를 복사할 때 `granite.config.ts`는 반드시 `@apps-in-toss/web-framework/config` 기반 최신 구조로 맞춰야 한다. 예전 `@apps-in-toss/framework/config` 형태를 쓰면 `ait build`가 RN 번들 생성 경로에서 실패할 수 있다.
- 새 앱에서 `npm install`만 실행하면 peer dependency/CLI 호환 문제가 날 수 있으므로, seed 앱의 `package.json`/`package-lock.json` 조합을 유지하고 필요 시 `npm ci --legacy-peer-deps`를 사용한다. `npm audit fix --force`는 사용하지 않는다.
- 탭 게임형 앱은 룰렛형보다 구현이 빠르고 반복 진입 루프를 만들기 쉽다. 핵심 상태는 `home → hunt → result`, 탭 HP, 결과 루틴 카드, 30일 기록이면 충분하다.
