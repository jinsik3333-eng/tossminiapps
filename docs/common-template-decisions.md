# Common Template Decisions

## 공통 리텐션/광고 구조

- 모든 앱은 홈에 알림/로그인 nudge를 둔다.
- 모든 앱은 보조 체리피킹 메뉴를 둔다.
- 광고 CTA는 현금/포인트/보상 표현 대신 `루틴 카드`, `추가 단서`, `체크리스트` 같은 콘텐츠 보상형 표현을 사용한다.
- 결과 화면에는 오늘의 단서, 오늘의 루틴, 반복 CTA, 광고 후 추가 콘텐츠를 둔다.

## 앱 타입별 기본 구조

- 룰렛형: 중앙 큰 룰렛 회전 → 멈춤 → 선택/결과 reveal.
- 탭 게임형: 홈 → 탭 HP 감소 → 포획/완료 → 결과 루틴 카드.
- 테스트형: 질문 4~6개 → 결과 유형 → 결과별 이미지/루틴 카드.
- Toss 캐주얼 게임형: 로딩/프로필 확인 → 랜덤 수집/점수 보너스가 보이는 게임 홈 → 1회 튜토리얼 → 플레이 HUD/보드 → 랜덤 획득 결과/랭킹/보상형 광고 CTA. 일반 미니앱 TDS 카드보다 큰 보드, 두꺼운 외곽선, 고채도 버튼, 게임센터 adapter를 우선한다.
- 3매치류 보드 조작: 모바일 기본값은 스와이프/드래그로 인접 칸 교체, 클릭-클릭은 보조 조작으로 유지한다. 타일에는 `touch-action: none`을 적용해 스크롤 제스처와 충돌을 줄인다.

## lane defense 게임 템플릿 결정

- Toss 캐주얼 디펜스형 기본 흐름은 `home → tutorial/profile gate → play → result`로 둔다.
- 홈 리텐션 요소는 오늘 웨이브, 최근 7일 기록, 수집 진행률, 리더보드/fallback 상태, 하단 광고 슬롯이다.
- 플레이는 30초·HP 5·3 lane·탭 제거·콤보 8 스킬 1회 구성을 MVP 기본값으로 한다.
- CSS monster/token 방식으로 toy/clay 느낌을 만들고, 대량 이미지 생성은 대표 샘플 승인 전까지 보류한다.
- Game Center adapter는 local/sandbox/unsupported에서 inline 메시지만 보여주고 게임 진행을 막지 않는다.

## 2026-05-07 — 테스트형 앱 보조 메뉴 위치

- 결정: 테스트형 앱의 보조 메뉴/체리픽 메뉴는 intro가 아니라 result 하단에 둔다.
- 이유: 사용자는 먼저 진단 완료와 결과 확인을 기대하므로, 시작 전 보조 메뉴는 진입 집중도를 낮춘다.
- 구현 규칙: 보조 메뉴 컴포넌트는 label 배열이 아니라 `{ label, onClick }` 액션 배열을 받게 해 실기기 테스트에서 무동작 버튼이 생기지 않게 한다.

## 2026-05-07 — WebView 앱 브랜드 아이콘 공통 규칙

- 결정: 모든 WebView 미니앱은 `public/app-icon.png`를 앱별 고유 아이콘으로 두고, `granite.config.ts`의 `brand.icon`은 `https://{appName}.apps.tossmini.com/app-icon.png` 형식으로 채운다.
- 이유: `brand.icon` 빈 값은 Apps in Toss 검수에서 콘솔 등록 아이콘과 불일치로 반려될 수 있다.
- 운영: AIT 업로드 전 콘솔 앱 정보의 브랜드 아이콘에 같은 PNG를 업로드하고, `npm run build` 산출물을 새로 등록한다.

## 2026-05-07 — 보조 메뉴와 광고 게이트 분리

- 결정: 결과 화면의 보조 메뉴 버튼은 광고 영상으로 보내지 않는다. 광고는 `광고 보고 ...`처럼 명시된 단일 보상 CTA에서만 선택적으로 실행한다.
- 이유: 여러 보조 메뉴가 모두 광고로 이어지면 사용자는 무동작/광고 유도 UI로 인식한다. 검수/UX 관점에서도 앱 기능과 광고 지점이 분리되어야 한다.
- 구현 규칙: `CherryPickMenu`류 컴포넌트는 `string[]`가 아닌 `{ label, onClick }[]`를 받고, 모든 버튼에 실제 액션을 연결한다. 제작자 관점 문구(`매일 들어올 이유`, `리텐션`)와 보조 메뉴 내부 `AD ·` 문구는 사용하지 않는다.

## 2026-05-08 — 혜택 루프와 배너 수익화 기본형

- 결정: `패치 붙이기` 같은 모호한 버튼명 대신 `혜택 루틴 열기 n/3`처럼 누르면 무엇이 열리는지 버튼에 직접 쓴다.
- 결정: 결과 화면 보조 메뉴는 `오늘의 보조 메뉴`가 아니라 `결과 활용하기`처럼 사용자 가치 중심 이름을 쓴다.
- 결정: 수익화는 화면별 상시 배너 + 명시적 보상형 CTA를 조합한다. 배너는 시작/문항/결과 화면에 배치하고, 보상형 광고는 상세 처방/배지 완성처럼 사용자가 광고 시청을 예상할 수 있는 버튼에만 연결한다.
- 근거: Apps in Toss 배너 광고 문서는 WebView 배너 컨테이너 width 100%, 고정형 height 96px 권장 및 SDK 초기화/attach/destroy 흐름을 안내한다.

## 2026-05-29: 게임 출시 패키지 공통 규칙

- 결정: 게임 앱은 코드 빌드 통과만으로 출시 준비 완료로 보지 않고, `.ait` 압축해제 크기, 콘솔 이미지 규격, `brand.icon`, 리더보드/등급분류/실기기 테스트 잔여 작업을 한 패킷으로 관리한다.
- 결정: 콘솔 업로드 자산은 `assets/app-store/{appName}/`에 모으고, 앱 런타임 확인용 이미지는 각 앱 `public/`에 복사한다.
- 구현 규칙: 게임 6개 묶음은 `python3 scripts/create_mongle_game_appstore_assets.py`로 자산을 재생성하고 `python3 scripts/check_store_assets.py '0[7-9]-*' '1[0-2]-*'`로 규격을 검증한다.
- 운영: 광고 SDK가 실제로 연결되기 전에는 사용자 화면에 `광고 보고` CTA나 광고 placeholder를 노출하지 않는다. 리더보드는 콘솔 승인 전 오류와 샌드박스 점수 미반영을 정상 제약으로 보고 실기기 QA에서 별도 확인한다.

## 2026-05-29: 캐주얼 게임 공통 UX/광고 규칙

- 결정: 모든 캐주얼 게임은 `home -> play -> result` 흐름 안에 `StageRail`을 둔다. 홈과 플레이는 현재 단계/다음 목표를 보여주고, 결과는 다음 판 진입 이유를 보여준다.
- 결정: 하단 배너는 상시 슬롯으로 두고, 전면/보상형 광고는 결과 이후 `다음 판` 진입 시점에만 선택적으로 연다. 광고가 준비되지 않았거나 로컬 브라우저라면 바로 다음 판으로 fallback한다.
- 결정: 실제 광고 그룹 ID는 env로만 주입한다. 소스와 `.env.example`에는 테스트 광고 ID를 넣지 않는다.
- 구현 규칙: 광고 훅을 쓰는 게임 앱은 `TDSMobileAITProvider`를 `main.tsx`에 적용한다. Provider 누락은 로컬 Chrome에서 빈 화면으로 이어질 수 있다.
- 구현 규칙: 캐릭터는 `public/game-assets/*.png`를 기본으로 쓰고, 보드 내부 핵심 플레이어는 CSS 도형이 아니라 이미지 에셋으로 렌더링한다.

## 2026-05-29: 캐주얼 게임 레벨 설계 규칙

- 결정: 단계는 UI copy가 아니라 실제 플레이 파라미터다. 새 몽글류 게임은 `*_STAGE_EFFECTS`, `*_LEVELS`, `*_RULES` 같은 데이터 배열로 단계별 차이를 먼저 정의한다.
- 결정: 러너류는 속도/스폰/위험물 비율, 점프류는 안전구간/퍼펙트존/보상 주기, 미로류는 맵/열쇠/조각/함정 배치를 단계별로 바꾼다.
- 결정: 탐정/관찰류는 고정 role 찾기가 아니라 공개 단서 속성의 조합 매칭으로 만든다. 정답 여부를 `thief` 같은 CSS class로 노출하지 않는다.
- 구현 규칙: 회귀 스크립트는 단계 데이터 존재와 이전 단순 판별 문자열 제거를 같이 검사한다. 레벨 레일만 있는 앱은 출시 전 완료로 보지 않는다.

## 2026-05-31: 3매치 손맛/아이템 규칙

- 결정: 3매치 게임은 3개 기본 제거, 4개 큰 보너스, 5개 대폭발, 가로세로 동시 매치 보너스를 서로 다른 점수/임팩트로 표현한다.
- 결정: 매치 제거 후 타일이 떨어져 새 3개 이상 줄이 생기면 캐스케이드로 다시 제거한다. 드롭/리필 후 매치가 없어질 때까지 반복 판정한다.
- 결정: 현재 매치가 없고 가능한 인접 스왑도 0개인 정체 보드는 자동 셔플한다. 셔플 결과는 즉시 터지는 줄 없이 다음 매치 후보가 최소 1개 있어야 한다.
- 결정: 특수 매치는 다음 턴에 쓰는 이미지형 아이템을 지급한다. 가로 4개는 가로 줄 삭제, 세로 4개는 세로 줄 삭제, 2x2는 3x3 폭발, 5줄은 같은 블록 전체 삭제, 셔플은 즉시 보드 섞기로 둔다.
- 결정: 동물류만 반복하면 애니팡류와 겹치고 키보드 이모지는 허접해 보이므로, 기본 블록은 말랑 디저트/장난감/보석 소품처럼 직접 만든 이미지 에셋 조합으로 먼저 시도한다.
- 결정: 게임 중 배경은 카드 안의 단순 그라데이션이 아니라 플레이 화면 전체에 깔리는 레이어형 배경이어야 한다. 보드와 HUD는 그 위에 떠 있는 구조로 둔다.
- 결정: 사운드는 효과음만으로는 부족하다. 사용자의 첫 탭 이후 루프형 BGM을 켜고, 설정에서 BGM/효과음/진동을 분리해 제어한다.
- 결정: 진동은 Apps in Toss WebView의 `generateHapticFeedback`을 1순위로 쓰고, 일반 브라우저 QA에서는 `navigator.vibrate` fallback으로만 보완한다.
- 결정: 캐주얼 퍼즐 UI는 갈색 반투명 외곽선, 유광 엠보 버튼, 레이어형 숲/정글 배경, 팝/플래시/보드 흔들림 애니메이션을 기본 손맛 장치로 둔다.
- 결정: 퍼즐/스테이지형 게임 첫 화면은 랜덤 캐릭터 이벤트가 아니라 `현재/전체 단계`, 보드 미리보기, 다음 보상, 시작 CTA가 보이는 로비여야 한다.
- 구현 규칙: 매치 분석, 점수 계산, 아이템 지급, 아이템 사용은 UI와 분리한 순수 로직으로 두고 `node --test` 회귀 테스트를 붙인다.
- 광고 규칙: 결과 배너와 보상형 CTA는 실제 광고 ID가 있을 때만 SDK를 호출한다. 로컬/미설정 상태에서는 사용자에게 광고 placeholder를 보여주지 않는다.
- 광고 규칙: 보상형 광고는 SDK 완료/보상 이벤트에서만 아이템이나 이동 수를 지급한다. 미준비 상태는 숨김 또는 준비 안내로 처리하고 별도 연습 보상은 만들지 않는다.

## 2026-05-31: 캐주얼 게임 메뉴 에셋 규칙

- 결정: 게임 메뉴 버튼은 PNG 통이미지로 만들지 않는다. 한글 텍스트, 줄바꿈, 비활성/눌림 상태, 390px 반응형은 CSS와 DOM이 관리한다.
- 결정: 앱다운 재질감은 타이틀 플라크, 닫기 버튼, 기능 아이콘, 패널 코너 장식처럼 교체 가능한 PNG 에셋에서 만든다.
- 구현 규칙: imagegen 산출물은 원본을 보존하고, 앱에는 crop/투명화된 개별 PNG를 둔다. 적용 후 브라우저에서 이미지 로드 개수, naturalWidth, overflow-x, title/close bounding box를 수치로 확인한다.

## UI 표준: 한 화면 한 행동 원칙

토스 미니앱의 모든 일반앱/비게임 앱 화면은 아래 7개 원칙을 기본 판정 기준으로 삼는다.

1. 첫 화면에서 앱의 목적을 바로 알 수 있게 하기
2. 주요 행동 버튼을 하나만 또렷하게 두기
3. 입력은 최대한 줄이고 기본값을 제공하기
4. 화면 이동 흐름을 짧게 만들기
5. 저장·로딩·실패·완료 상태 피드백을 즉시 보여주기
6. 빈 화면·에러 화면에도 다음 행동을 넣기
7. 비슷한 기능은 같은 패턴으로 반복하기

### 적용 방식

- 첫 화면에는 “무엇을 하는 앱인지”와 “지금 누를 버튼”이 바로 보여야 한다.
- 광고/리워드/알림/크로스앱 이동은 사용자의 다음 행동을 흐리게 하지 않고, 보상 맥락에서 제공한다.
- 리워드 허브형 화면도 한 번에 여러 버튼을 난사하지 않고, 대표 CTA 1개와 보조 행동 묶음으로 구성한다.
- 각 앱의 결과 화면은 “결과 확인 → 광고 보고 보상/루틴 받기 → 다른 앱/내일 재방문” 흐름을 짧게 유지한다.
- 앱별 차이는 콘텐츠와 캐릭터만 바꾸고, 버튼/피드백/광고 보상 패턴은 공통화한다.
